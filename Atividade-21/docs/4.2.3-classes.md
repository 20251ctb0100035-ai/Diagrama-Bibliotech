# 4.2.3 Modelagem de Classes

## Dos substantivos às classes

As classes saem dos substantivos do fluxo principal de **Registrar Encomenda** (UC03) especificado na 4.2.2 e da lista de Requisitos Funcionais da 4.2.1. Cada coisa que a confeiteira informa ou que o sistema valida e registra é algo que o sistema precisa guardar.

Nem todo substantivo vira classe. Aplicamos três filtros: o que é detalhe vira atributo; o que é interface (telas, botões) não entra; o que está fora do sistema (caderno, WhatsApp) também não entra.

| Substantivo | De onde veio | Vira | Por quê |
|---|---|---|---|
| confeiteira | Ator da 4.2.2, RNF03 | classe **Usuario** | É a operadora do sistema que precisa se autenticar para registrar pedidos e gerenciar produtos. |
| cliente | Passo 3 do UC03, RF01 | classe **Cliente** | O sistema precisa guardar o nome e contato de quem fez a encomenda. |
| produto, bolo | Passo 3 do UC03, RF02 | classe **Produto** | Itens do cardápio cadastrados com preço base que compõem os pedidos. |
| encomenda, pedido | Passo 5 do UC03, RF03 | classe **Encomenda** | Registro central que vincula cliente, data/hora de entrega, status e valor total. |
| item, quantidade | Passo 3 e 4 do UC03 | classe **ItemEncomenda** | Guarda a quantidade e preço negociado de um produto específico em um pedido. *Nasceu da especificação do fluxo do UC03*. |
| data e hora de entrega | Passo 3 do UC03, RF03 | atributo de **Encomenda** | É um detalhe da encomenda, não existe isoladamente. |
| status | Passo 5 do UC03, RF05 | atributo de **Encomenda** | Detalhe que indica o estágio (Pendente, Em Produção, Entregue, Cancelada). |
| preço base | RF02 | atributo de **Produto** | Valor padrão do item no cardápio. |
| caderno, WhatsApp | Falas da 4.1 e 4.2.1 | nada | Estão fora do sistema. O WhatsApp é onde a conversa ocorre e o caderno é o que o sistema substitui. |

## Classes

Quatro classes formam a estrutura central do DoceAgenda. Cada uma é descrita abaixo com seus atributos (`nome: tipo`), operações com parênteses `()` e a origem rastreável na 4.2.1/4.2.2.

| Classe | Atributos | Operações | Veio de |
|---|---|---|---|
| **Cliente** | - id: int<br>- nome: String<br>- telefone: String | + cadastrar(): void<br>+ atualizarDados(): void | RF01, UC03 (Passo 3), FA01 |
| **Produto** | - id: int<br>- nome: String<br>- precoBase: double | + cadastrar(): void<br>+ atualizarPreco(): void | RF02, UC03 (Passo 3) |
| **Encomenda** | - id: int<br>- dataHoraEntrega: DateTime<br>- status: String<br>- valorTotal: double | + registrar(): void<br>+ calcularTotal(): double<br>+ atualizarStatus(): void | RF03, RF05, UC03 (Passos 4, 5 e 6), FE01 |
| **ItemEncomenda** | - quantidade: int<br>- precoPraticado: double | + subtotal(): double | UC03 (Passo 4 - especificação do diálogo) |

## Diagrama de classes

**Figura 2 – Diagrama de classes do DoceAgenda**

![Diagrama de classes do DoceAgenda](../diagramas/classes.png)

Fonte: Autoria própria (2026).

A Figura 2 apresenta a estrutura estática do DoceAgenda através de três associações e uma composição:

- **Associações:** 
  - Um `Cliente` faz zero ou várias (`0..*`) `Encomenda`. Cada `Encomenda` pertence a exatamente um (`1`) `Cliente`.
  - Um `Produto` está presente em zero ou vários (`0..*`) `ItemEncomenda`. Cada `ItemEncomenda` refere-se a exatamente um (`1`) `Produto`.
- **Composição (Losango Cheio):** 
  - A relação entre `Encomenda` e `ItemEncomenda` é de **Composição** (losango preenchido do lado de `Encomenda`). 
  - *O teste que decidiu o losango:* Se uma `Encomenda` for excluída ou cancelada fisicamente do banco de dados, os seus `ItemEncomenda` perdem o sentido e deixam de existir. Um item de encomenda sem o pedido pai não existe sozinho no sistema.
  - A multiplicidade `1 <---> 1..*` indica que toda `Encomenda` precisa ter no mínimo um `ItemEncomenda`.
- **Herança:** 
  - Não há estrutura de herança no modelo atual do DoceAgenda, pois o sistema é de uso exclusivo da confeiteira e não existem sub-tipos distintos de clientes ou produtos que justifiquem especialização.

## Teste de objetos

Para validar as multiplicidades e a promessa do diagrama de classes, testamos uma situação real da rotina da Mariana.

**A situação:** A cliente *Ana Silva* fez uma encomenda para o dia 20/11/2026 contendo 2 unidades do *Bolo de Morango* (R$ 80,00 cada). Semanas antes, Ana já havia feito outro pedido de doces que foi devidamente entregue.

**Figura 3 – Diagrama de objetos: uma encomenda real no DoceAgenda**

![Diagrama de objetos do DoceAgenda](../diagramas/objetos.png)

Fonte: Autoria própria (2026).

| Objeto | Classe | Valores |
|---|---|---|
| `c1` | Cliente | id = 1, nome = "Ana Silva", telefone = "(42) 99999-1111" |
| `p1` | Produto | id = 10, nome = "Bolo de Morango", precoBase = 80.00 |
| `e1` | Encomenda | id = 99, dataHoraEntrega = "2026-10-01 14:00", status = "Entregue", valorTotal = 50.00 |
| `e2` | Encomenda | id = 100, dataHoraEntrega = "2026-11-20 15:00", status = "Pendente", valorTotal = 160.00 |
| `ie1` | ItemEncomenda | quantidade = 2, precoPraticado = 80.00 |

**Ligações:** `c1` e `e1`, `c1` e `e2`, `e2` e `ie1`, `ie1` e `p1`.

**O que o teste confirma:**

- **Um cliente faz várias encomendas:** A cliente `c1` (Ana) está ligada a duas encomendas distintas (`e1` e `e2`). Se tivéssemos definido multiplicidade `1` do lado da `Encomenda`, este caso real quebraria o modelo.
- **Toda encomenda pertence a um único cliente:** Tanto `e1` quanto `e2` possuem exatamente uma linha de ligação para `c1`.
- **Uma encomenda possui um ou mais itens:** A encomenda `e2` possui a composição com o item `ie1`.
- **Separação entre Produto e ItemEncomenda:** O produto `p1` (Bolo de Morango com preço base R$ 80) é referenciado pelo item `ie1` com sua `quantidade = 2`. Isso confirma que `ItemEncomenda` é essencial para multiplicar a quantidade pelo preço sem alterar o cadastro original do produto.

## Rastreabilidade com a 4.2.2

| Operação ou atributo | Classe | De onde veio |
|---|---|---|
| cadastrar(), atualizarDados() | Cliente | RF01 e Fluxo Alternativo FA01 |
| cadastrar(), atualizarPreco() | Produto | RF02 |
| registrar(), calcularTotal() | Encomenda | Passo 4 e 6 do fluxo principal do UC03 |
| atualizarStatus() | Encomenda | RF05 |
| subtotal() | ItemEncomenda | Passo 4 da especificação do UC03 |
| dataHoraEntrega, status | Encomenda | Passo 3 do UC03 e RF03/RF05 |
| quantidade, precoPraticado | ItemEncomenda | Passo 3 e 4 do UC03 |

**Conclusões da rastreabilidade:**
- **Toda operação tem origem:** Não foi inserida nenhuma operação ou atributo "fantasma" sem respaldo em requisito funcional (4.2.1) ou passo do caso de uso (4.2.2).
- **Todo passo do sistema tem casa:** Os passos de cálculo, validação e gravação do UC03 encontraram execução explícita nas operações `calcularTotal()`, `subtotal()` e `registrar()`.
- **O que a modelagem mudou:** A especificação do diálogo revelou a necessidade da classe `ItemEncomenda` (que não figurava explicitamente na lista simplificada de RFs da 4.2.1), resolvendo a modelagem de cardinalidade muitos-para-muitos entre `Encomenda` e `Produto`.
